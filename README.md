# Alby Hub on StartOS

> Everything not listed in this document should behave the same as upstream
> Alby Hub. If a feature, setting, or behavior is not mentioned here, the
> upstream documentation is accurate and fully applicable — see the
> Documentation section of `instructions.md` for links.

[Alby Hub](https://github.com/getAlby/hub) is a self-custodial Lightning wallet with Nostr Wallet Connect and an app marketplace. On StartOS its Lightning backend is chosen once at install — either a node already running on this server, or one of Alby Hub's own embedded nodes — and every address and credential for an on-server backend is resolved by the package rather than typed in.

- **Upstream repo:** <https://github.com/getAlby/hub>
- **Wrapper repo:** <https://github.com/Start9Labs/albyhub-startos>

## Image and Container Runtime

The upstream image is used unmodified, with its own entrypoint, and one subcontainer runs the whole service.

| Property      | Value                                                            |
| ------------- | ---------------------------------------------------------------- |
| Image         | `ghcr.io/getalby/hub`                                            |
| Architectures | x86_64, aarch64                                                  |
| Entrypoint    | Upstream default, run as the container's init process            |
| Subcontainer  | `albyhub-sub` — the `primary` daemon, and the one to `attach` to |

## Volume and Data Layout

Two volumes, and one of them never enters the container. Depending on the chosen backend, a third mount appears — a read-only view of another service's data.

| Volume    | Mount Point   | Purpose                                                                               |
| --------- | ------------- | ------------------------------------------------------------------------------------- |
| `main`    | `/data`       | Alby Hub's working directory: its database, and the embedded LDK or Bark node's state |
| `startos` | — (host side) | `store.json`; never mounted into the container                                        |

| Backend  | Read-only mount | Source                                                                               |
| -------- | --------------- | ------------------------------------------------------------------------------------ |
| LND      | `/mnt/lnd`      | LND's `public` volume, `admin/` — `admin.macaroon` and `tls.cert`                    |
| CLN      | `/mnt/cln`      | Core Lightning's `public` volume, `grpc/` — `ca.pem`, `client.pem`, `client-key.pem` |
| phoenixd | `/mnt/phoenixd` | phoenixd's `public` volume, `full/` — `http-password`                                |

The embedded backends mount nothing extra: LDK and Bark keep their state under `/data` like the rest of the wallet.

## File Models

One model, holding the backend choice everything else in the package is derived from, the LDK node's Electrum server, and the setup code.

| File         | Format | Modelled                | Written by                                                                            |
| ------------ | ------ | ----------------------- | ------------------------------------------------------------------------------------- |
| `store.json` | JSON   | Yes — `FileHelper.json` | Init (`SETUP_CODE`), the Set Lightning Implementation and Set Electrum Server actions |

- `LN_BACKEND_TYPE` is the chosen backend, one of `LND`, `CLN`, `PHOENIX`, `LDK`, or `BARK`.
- `ELECTRUM_SERVER` is the LDK node's chain source, one of `fulcrum`, `electrs`, or `alby`; `null` for every other backend.
- `SETUP_CODE` is a random 16-character code, generated by init whenever it is absent — at install, and on the first init of an install that predates it.

It lives on the `startos` volume so it is never visible to the application, which has no say in it.

**No upstream configuration is written.** Alby Hub is configured entirely by environment, and the package composes that environment fresh on every start rather than persisting it:

| Variable                                            | When                | Value                                                                           |
| --------------------------------------------------- | ------------------- | ------------------------------------------------------------------------------- |
| `LN_BACKEND_TYPE`                                   | always              | From `store.json`                                                               |
| `SETUP_CODE`                                        | always              | From `store.json`                                                               |
| `WORK_DIR`                                          | always              | `/data`                                                                         |
| `HIDE_UPDATE_BANNER`                                | always              | `true` — updates come from the registry, not from inside the app                |
| `ENABLE_ADVANCED_SETUP`                             | on-server backends  | `false` — the address and credentials are resolved, not entered                 |
| `LND_ADDRESS`, `LND_CERT_FILE`, `LND_MACAROON_FILE` | LND                 | Bridge address, plus paths into the read-only LND mount                         |
| `CLN_ADDRESS`, `CLN_LIGHTNING_DIR`                  | CLN                 | Bridge address, plus `/mnt/cln`                                                 |
| `PHOENIXD_ADDRESS`, `PHOENIXD_AUTHORIZATION`        | phoenixd            | Bridge address, plus the contents of `/mnt/phoenixd/http-password` at start     |
| `LDK_ELECTRUM_SERVER`                               | LDK, local Electrum | `tcp://` plus the Fulcrum or Electrs plaintext bridge address; unset for `alby` |

Alby Hub copies these into its own database at start, overwriting the stored connection values for LND, Core Lightning, and phoenixd every time. A rotated credential or moved address takes effect on Alby Hub's next restart. The phoenixd password is read at start time only: after changing it with phoenixd's Set API Password, restart Alby Hub. If `http-password` is unreadable, the daemon fails to start rather than starting unauthenticated.

## Dependencies

All five are declared optional in `startos/dependencies.ts`, each enabled by the backend choice, so at most one is active: a node for LND, Core Lightning or phoenixd, an Electrum server for LDK unless it uses Alby's, and nothing for Bark.

| Backend | Dependency    | Version           | Kind      | Health checks required       | Mount                      |
| ------- | ------------- | ----------------- | --------- | ---------------------------- | -------------------------- |
| LND     | `lnd`         | `>=0.21.6-beta:3` | `running` | `lnd`, `sync-progress`       | `/mnt/lnd`, read-only      |
| CLN     | `c-lightning` | `>=26.6.10:3`     | `running` | `lightningd`, `check-synced` | `/mnt/cln`, read-only      |
| PHOENIX | `phoenixd`    | `>=0.9.2:4`       | `running` | `primary`                    | `/mnt/phoenixd`, read-only |
| LDK     | `fulcrum`     | `>=2.1.1:8`       | `running` | `primary`, `sync-progress`   | —                          |
| LDK     | `electrs`     | `>=0.11.1:11`     | `running` | `electrs`, `sync`            | —                          |
| BARK    | none          | —                 | —         | —                            | —                          |

The sync checks are required as well as "running", so Alby Hub waits for a node or Electrum server that is up but still catching up. For LDK, `fulcrum` or `electrs` is enabled only when `ELECTRUM_SERVER` names it.

LDK reads the chain from the Electrum server in `ELECTRUM_SERVER`; with `alby` the package leaves `LDK_ELECTRUM_SERVER` unset, so upstream's default, Alby's `ssl://electrum.getalbypro.com:50002`, applies. The embedded backends otherwise reach third-party servers on upstream defaults the package does not set: LDK takes inbound liquidity from Lightning service providers (an LSPS2 provider from Alby's channel-peer suggestions, Megalith otherwise), and, for a node created with a paid Alby account, stores its channel state on Alby's VSS server (`LDK_VSS_URL`, `https://vss.getalbypro.com/vss`). Bark uses Second's Ark and Esplora servers.

Addresses are resolved over the local service bridge from each dependency's own host binding rather than by hostname, and `main` holds that resolution in a reactive `const`. So Alby Hub restarts when the backend's address genuinely moves — installed, uninstalled, re-ported — and not when the backend merely updates. If the backend is not reachable when Alby Hub starts, `main` throws with a message naming it rather than starting a wallet that cannot see its node.

## Network Access and Interfaces

One interface, serving the wallet UI. Nothing is exported for dependent services.

| Interface | Id     | Type | Port | Description                |
| --------- | ------ | ---- | ---- | -------------------------- |
| Web UI    | `main` | ui   | 8080 | The Alby Hub web interface |

The port is bound on the `main` MultiHost and is not masked. Note that the interface id is `main`, not `ui`.

An install carried over from StartOS 0.3.5 also had port 8443 bound on `main`, that version's in-container TLS proxy. The `1.24.1:0` migration retires it; the `main` host keeps its addresses, including any Tor address, on 8080.

## Installation and First-Run Flow

Install generates the setup code and starts no service. It also raises a `critical` task, because the package cannot choose a Lightning backend on your behalf and cannot start without one.

The ordering that matters: **install and start the backend service first**, then make the choice. `main` refuses to start when `LN_BACKEND_TYPE` is unset, and refuses again if the selected backend is not yet reachable on the internal network. The same holds for LDK with Fulcrum or Electrs, the form's default; LDK with Alby's Electrum server, and Bark, have no dependency.

Wallet setup itself — the password, the onboarding flow — happens inside Alby Hub's own UI on first login. Until it completes, Alby Hub requires the setup code (`X-Setup-Code`) on `POST /api/setup`, `/api/setup/verify-code` and `/api/restore`, and its UI asks for it first; once setup has completed, upstream ignores the code. The Set Lightning Implementation result and the Show Setup Code action both display it.

## Actions

Three actions: one raised only by its task, one listed only for the LDK backend, and one always listed.

### Set Lightning Implementation — hidden

**Not in the Actions list.** It is `visibility: 'hidden'` and reachable only through the task that raises it, so a user is never told to go and find it. It is also `only-stopped`, because the value it writes is read as the service starts.

- **Default:** none — the form opens with no backend selected, so the task cannot be submitted until one is picked. Picking LDK reveals the Electrum server choice (the Set Electrum Server field), defaulting to Fulcrum.
- **What it changes:** `LN_BACKEND_TYPE`, and `ELECTRUM_SERVER` for LDK, in `store.json`, which in turn decides the package's dependency set, its mounts, and the environment handed to the application.
- **Result:** the setup code, masked and copyable.
- **Repeat safety:** effectively one-way. Nothing in the package prevents a second write, but once the task is cleared there is no route to the action in the UI, and a wallet's funds and channel state belong to the backend it was created against — pointing an existing install at a different one does not migrate them.

### Set Electrum Server

- **Visibility and status:** in the Actions list only with the LDK backend; `only-stopped`, since `main` reads the value at start.
- **Input:** Fulcrum on this server (default), Electrs on this server, or Alby's Electrum server; prefilled with the current choice.
- **What it changes:** `ELECTRUM_SERVER` in `store.json`, and with it the LDK dependency and `LDK_ELECTRUM_SERVER`.
- **Repeat safety:** safe to change at any time; every choice serves the same chain, and the wallet's state is untouched.

### Show Setup Code

- **Visibility and status:** enabled, any status.
- **Result:** the setup code from `store.json`, masked and copyable. It changes nothing; after onboarding the code no longer has any effect.

## Tasks

Two tasks, each blocking the service until completed.

| Task                         | Severity   | Raised when                                                                                                                                            | Cleared when    |
| ---------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------- |
| Set Lightning Implementation | `critical` | At install                                                                                                                                             | The action runs |
| Set Electrum Server          | `critical` | On any init but install, while the backend is LDK and `ELECTRUM_SERVER` is unset — an LDK install from before the choice existed, on update or restore | The action runs |

`critical` suspends the ordinary controls, so a fresh install presents only this prompt rather than a start button — the intended experience, not a fault, since starting without a backend could not work.

## Health Checks

One check, on the primary daemon.

| Check                     | Method                 | Grace Period |
| ------------------------- | ---------------------- | ------------ |
| `primary` "Web Interface" | Port 8080 is listening | SDK default  |

It confirms the web server is up, which for an on-server backend also implies the backend was reachable at start — the daemon would not have got this far otherwise. A failure after a period of running therefore points at the application, not at the backend; a failure to start at all is more likely the backend, and the service logs carry the explicit message.

## Backups and Restore

Both volumes are copied wholesale — `sdk.Backups.ofVolumes('main', 'startos')` — with SQLite's transient sidecar files excluded, since capturing a `-wal` or `-shm` alongside its database would restore a torn snapshot rather than a clean one.

- **Included:** Alby Hub's database, app connections and Nostr Wallet Connect settings, the embedded LDK or Bark node's state if one is in use, and `store.json` — the backend choice and the setup code.
- **Excluded:** `*-journal`, `*-wal`, `*-shm`.
- **Restore:** the backend choice comes back with the wallet, so the package resolves the same dependency as before — which must be installed and running for the service to start. For an on-server backend, the node's own funds and channels are that package's backup, not this one's; only Alby Hub's view of them lives here.
- **Stale LDK state:** with the LDK backend the backup carries live channel state under `/data`. Restoring anything but the most recent backup, or running the original install again after restoring elsewhere, broadcasts revoked state, which a peer can punish by claiming the whole channel balance. StartOS shows no warning at restore; `instructions.md` carries it.

## Limitations and Differences

1. **The backend is chosen once.** The action that sets it is hidden after its task is cleared, and no migration path exists between backends.
2. **On-server backends only — no address field.** LND, Core Lightning, and phoenixd are reached at addresses the package resolves from the local dependency; upstream's advanced setup, where a remote node's address and credentials are typed in, is switched off for these backends.
3. **The phoenixd password is read from its config file at start**, so that mount must be readable; there is no way to supply the credential by hand. Restart Alby Hub after changing the password in phoenixd.
4. **The LDK backend's chain source is an Electrum server** — Fulcrum, Electrs, or Alby's. Bitcoin's RPC (`LDK_BITCOIND_RPC_*`) and Esplora are not offered, nor an Electrum server off this box.
5. **The in-app update banner is suppressed.** Updates arrive through the StartOS registry, so upstream's prompt would point at the wrong mechanism.
6. **No riscv64 build.** x86_64 and aarch64 only.

## Quick Reference for AI Consumers

```yaml
package_id: albyhub
image: ghcr.io/getalby/hub
architectures:
  - x86_64
  - aarch64
subcontainers:
  - albyhub-sub
volumes:
  main: /data
  startos: host side (store.json)
file_models:
  - store.json # on the startos volume; holds LN_BACKEND_TYPE, ELECTRUM_SERVER and SETUP_CODE
startos_managed_env_vars:
  - LN_BACKEND_TYPE
  - SETUP_CODE
  - WORK_DIR
  - HIDE_UPDATE_BANNER
  - ENABLE_ADVANCED_SETUP # on-server backends only
  - LND_ADDRESS # LND only
  - LND_CERT_FILE # LND only
  - LND_MACAROON_FILE # LND only
  - CLN_ADDRESS # CLN only
  - CLN_LIGHTNING_DIR # CLN only
  - PHOENIXD_ADDRESS # phoenixd only
  - PHOENIXD_AUTHORIZATION # phoenixd only
  - LDK_ELECTRUM_SERVER # LDK with fulcrum or electrs only
dependencies: # at most one, decided by LN_BACKEND_TYPE and ELECTRUM_SERVER; none for BARK or LDK with alby
  - lnd
  - c-lightning
  - phoenixd
  - fulcrum
  - electrs
interfaces:
  main: { type: ui, port: 8080 }
actions:
  - set-lightning # hidden; raised by task only
  - set-electrum-server # LDK only
  - show-setup-code
tasks:
  - { action: set-lightning, severity: critical }
  - { action: set-electrum-server, severity: critical } # LDK installs without ELECTRUM_SERVER
health_checks:
  - primary # the daemon's ready check, displayed "Web Interface"
```
